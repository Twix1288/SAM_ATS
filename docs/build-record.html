Two display versions, and a data layer

There are exactly two ways Sam's read can be displayed on a candidate record, and they differ by who does the rendering. A third write puts the score into Ashby's own fields — that is not a display, it is what makes a scored candidate findable.

Why both

A gets read, B gets studied. The note is where a reviewer already is and needs no click, and Ashby renders embedded tables natively, so it carries the reasoning — just not the brand. The document is the Snapshot exactly as designed, behind one click. The note names the document, which turns two versions into one path rather than two competing ones.

The third write, /customField.setValues, is a different job entirely: neither display helps you find the right candidate among 41. Custom fields are what make the pipeline sortable.

The order is load-bearing. The note names the attachment, so the file lands first. Write the note first and it publishes a link to a document that does not exist yet. If the attachment fails, the note still ships and drops the reference rather than advertising a file nobody can open — and the run reports partial instead of claiming success.

Custom fields and a tag are the obvious next addition — the only versions Ashby can filter and sort, which matters across a pipeline rather than on one person. The assessment card is the one to chase, and it is waiting on partner approval. The resume slot is the one we will not take.

The one that mattered most

candidate.uploadResume writes the resume slot. Putting a Snapshot there risks displacing the document the candidate actually uploaded. candidate.uploadFile attaches ours alongside theirs instead. The resume-slot version is still built — as the one version shown specifically in order to refuse it.

Why these three and not one

They are not three versions of the same thing — they do different jobs. Custom fields are the only surface Ashby can sort and filter, so they are what actually puts a graded candidate into the dashboard. The note is the only one read without a click. The attachment is the only one carrying the quoted evidence behind every anchor. Drop any one and a real task gets harder.

Six further surfaces were investigated and left out — the assessment-partner card and the interview scorecard are the two worth revisiting, and both are waiting on Ashby.

05

The surface we refuse

Ashby has a dedicated resume endpoint, and it would render the Snapshot in the highest-traffic space on the whole record.

SurfaceEndpointWhy not
The resume slot/candidate.uploadResumeIt is the best-looking placement in Ashby and we will not use it. Ashby confirms this write forcefully replaces the candidate’s own resume in the main viewer, and no score is worth overwriting a document they uploaded themselves.

We use candidate.uploadFile instead, which appends to the candidate's files. Same PDF, same viewer, no risk of displacing a document the candidate owns — and the documentation does not say whether the resume write replaces or appends, which settles it.

The job description's hardest requirement — $5M+ in annualised invoice volume — maps to exactly one survey question, and that question collected no answers from anyone. A second requirement, competitive displacement, has no question at all. So 2 of 6 anchors are unobservable with this instrument, and every score in the mockup carries a coverage denominator for that reason.

This is why the engine distinguishes not collected from not met. Those mean opposite things to a hiring manager, and collapsing them is how a scoring product quietly becomes wrong.

07

Known gaps

Resume text extraction reads 29 of 42 documents

Built on node:zlib because the brief forbids new dependencies. Resumes using subset-embedded fonts without a usable ToUnicode map decode to glyph codes rather than characters; those are detected and dropped rather than returned as convincing-looking garbage. Career history renders when it parses and is omitted when it does not — it is never invented.

Scoring is deterministic and lexicon-based

No paid model, per the brief. It will miss paraphrase a model would catch. The mitigation is that low confidence is surfaced rather than smoothed over, and the evidence-span interface takes a model later without touching a single renderer.

Every pixel measurement is an estimate

Ashby publishes no dimensions, and one knowledge-base page explicitly declines to describe a strict panel layout. Region names, the tab list, the action bar and the location of custom fields are confirmed from their documentation. The sizes are not, and every "at real size" claim is an estimate until someone with an account confirms it.

08

Questions for Ashby

8 in total, ordered by blast radius. The 3 that would change what we build:

  • Custom fields as pipeline columns. Can a custom field be added as a column in the candidate pipeline or Application Review, and can candidates be sorted by its value?
  • Assessments Partner framework. Is the Assessments Partner framework available to us, or should Sam use the take-home flow (takeHomeAssignmentSubmitted → takeHomeAssignment.info → applicationFeedback.submit) instead?
  • candidateMerge. Does a merge carry third-party custom fields, files and notes onto the surviving candidate, or drop them?

The assessment question is the one worth leading with. The Assessments Partner framework renders a native card of typed, labelled values in Ashby's own style — structurally the closest fit to what Sam produces, and probably the surface Ashby built for products like this. If it is reachable it likely becomes the primary placement and everything else becomes a fallback.
